| 項目 | 内容 |
|---|---|
| バージョン | v0.3 |

---

## 1. 背景と目的

家族(2人)の夕食について、次の負担を減らす。

- 数日分の献立を考えること
- 冷蔵庫の余り物を使い切ること
- 品数の多い買い出しで、スーパーの中を行ったり来たりすること
- 美味しかった献立を忘れてしまうこと
- 栄養バランスがわからないこと

## 2. 利用者と利用環境

| 項目 | 内容 |
|---|---|
| 利用者 | 世帯の2人(どちらも使う。データは世帯単位で共有) |
| 家族構成 | 2人(27歳・31歳)。人数・年齢は設定で変更可 |
| 利用端末 | スマートフォンが中心 |
| 利用場面 | 自宅での献立計画、スーパーでの買い物 |

## 3. ユーザーストーリー

| ID | ストーリー |
|---|---|
| US-1 | 献立担当として、**開始日〜終了日を指定し、その期間の献立をまとめて提案**してほしい。考える負担を減らしたいから |
| US-2 | 献立担当として、**余り物リストを入力すると、それを優先して使う献立**を提案してほしい。食材を無駄にしたくないから |
| US-3 | 買い出し担当として、**期間中の食材を合算し、売り場ジャンル別に並んだ買い物リスト**が欲しい。店内を行ったり来たりしたくないから |
| US-4 | 家族として、**美味しかった献立をお気に入り保存**し、後から選べるようにしたい |
| US-5 | 家族として、**献立の栄養バランスについて根拠付きのアドバイス**が欲しい |
| US-6 | 献立担当として、**用事や外食がある日は「献立なし」に設定**し、提案や買い物の対象から外したい |
| US-7 | 献立担当として、**忙しい日は「時短」に設定し、簡単に作れるレシピ**を提案してほしい |
| US-8 | 家族として、**アレルギーや苦手な食材を登録**し、提案から外してほしい |

## 4. 機能要件

### 4.1 機能一覧(MoSCoW)

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| F1 | 献立提案 | 指定期間の各日に、日ごとのモードに沿って夕食を提案。気に入らない日・品だけ再提案できる | **Must** |
| F1a | 日ごとのモード設定 | カレンダー上で各日を `通常` / `時短` / `なし` に切り替え。初期値は `通常` | **Must** |
| F1b | 時短レシピ条件 | `時短` の日は調理時間の上限を守るレシピに限定 | **Must** |
| F2 | 余り物入力 | テキストで余り物を入力し、提案時に優先して使う | **Must** |
| F3 | 買い物リスト生成 | 献立の食材を算出 → 余り物を差し引き → 同じ食材を合算 → ジャンル別に並べる。`なし` の日は除外 | **Must** |
| F4 | 買い物チェック | 購入済みをチェックし、2人の端末間でリアルタイム同期 | **Must** |
| F5 | お気に入り保存 | 献立・レシピを保存し、評価・メモを付ける | **Must** |
| F13 | 家族設定 | メンバー(年齢・性別・身体活動レベル)、アレルギー、苦手食材を登録 | **Must** |
| F6 | 栄養サマリー | 期間中の栄養素を集計し、基準値と比較 | Should |
| F7 | 栄養アドバイス | 不足・過剰の指摘と改善案を出典付きで表示 | Should |
| F8 | お気に入りからの提案 | 保存済み献立を一定割合で提案に混ぜる | Should |
| F14 | 食材の使い回し提案 | 通常の日に多めに作り、時短の日にアレンジして使う提案 | Should |
| F9 | 売り場順カスタマイズ | 行きつけのスーパーの動線に合わせてジャンル順を変更 | Could |
| F10 | 余り物の写真入力 | 冷蔵庫の写真から食材を認識 | Could |
| F12 | 予定表の取り込み | Google カレンダーなどから外出予定を読み、`なし` / `時短` の候補を自動設定 | Could |
| F11 | 在庫管理 | 買った食材を在庫として自動追跡 | Won't(今回は対象外) |

**MVP = F1, F1a, F1b, F2, F3, F4, F5, F13**

### 4.2 献立の構成

対象は**夕食のみ**(データモデルは将来の朝食・昼食追加に備えて食事区分を持つ)。

| モード | 構成 | 調理時間 | 買い物リスト | 栄養集計 |
|---|---|---|---|---|
| `通常` | 主食+主菜+副菜+汁物(一汁二菜) | 制約なし | 対象 | 対象 |
| `時短` | **品数は柔軟**(下記参照) | **15分以内**(初期値、設定で変更可) | 対象 | 対象 |
| `なし` | 提案しない | ― | 対象外 | 対象外 |

`時短` の日は、一汁二菜にこだわらず品数を柔軟にする。調理時間の上限を優先し、例えば次のような構成を許容する。

1. 丼・麺などの**一品料理**(主食+主菜を兼ねる)のみ、または+簡単な汁物
2. 主菜+副菜を和えるだけ・電子レンジ調理に限定
3. 汁物を具だくさんにして副菜を兼ねる

栄養サマリーで不足が出る場合は、前後の `通常` の日で補う提案を行う(F7 と連携)。

### 4.3 計画期間

- 開始日〜終了日を指定する(日数は固定しない)
- 1回の計画期間の上限は 7〜10日で検討(LLM の提案品質を保つため)
- 傷みやすい食材(魚・葉物など)を使う献立と余り物を使う献立は、**期間の前半に寄せる**

### 4.4 買い物リストのジャンル(初期値)

野菜・果物 → 肉 → 魚 → 卵・乳製品 → 豆腐・練り物 → パン・米・麺 → 調味料・乾物 → 冷凍食品 → その他

### 4.5 家族設定(F13)

| 設定項目 | 用途 | 備考 |
|---|---|---|
| 名前・年齢 | 分量計算、栄養基準値の年齢区分 | 27歳は「18〜29歳」、31歳は「30〜49歳」の区分 |
| 性別 | 栄養基準値 | 値は後から入力でよい |
| 身体活動レベル | 推定エネルギー必要量 | 低い / ふつう / 高い |
| アレルギー食材 | **絶対除外**(ハード制約) | 現状なし |
| 苦手食材 | `never`(除外)/ `avoid`(頻度を下げる) | |
| 時短の上限時間 | 時短モードの条件 | 初期値 15分 |
| 夕食の比率 | 栄養目標の算出 | 初期値 1/3 |
| 予算 | 提案条件 | 現状は制約なし(枠のみ用意) |

## 5. 処理方針(LLM とロジックの分担)

| 処理 | 担当 | 理由 |
|---|---|---|
| 献立のアイデア・組み合わせ | LLM | 多様性、余り物への柔軟な対応 |
| 食材名の正規化(「玉ねぎ」「たまねぎ」→同一食材) | LLM + 辞書 | 表記ゆれ対策 |
| アレルギー・苦手食材の照合 | **ロジック** | LLM の見落としを防ぐ。違反があれば再生成 |
| 食材の合算・ジャンル分類 | ロジック | 決定的で検証可能 |
| 栄養価の計算 | ロジック(成分表データ) | 根拠を追跡できる |
| アドバイス文の生成 | LLM(計算結果と出典を入力として渡す) | 数値を捏造させない |

- LLM の出力は自由文ではなく **JSON スキーマ(料理名・区分・調理時間・食材名・分量・単位)** で構造化する

## 6. 栄養機能の根拠(F6, F7)

| データ | 発行元 | 用途 |
|---|---|---|
| 日本人の食事摂取基準 | 厚生労働省 | 年齢・性別ごとの推奨量・目標量 |
| 日本食品標準成分表 | 文部科学省 | 食品ごとの栄養素量 |

- アドバイスには「どの基準値と比べてどうか」を出典付きで表示する
- 夕食分の目標は「1日の基準値 × 夕食の比率(初期値 1/3)」とし、**これが仮定であることを画面に明示**する
- 疾患の食事療法など医療的な助言は対象外と明記する

## 7. 非機能要件

| 区分 | 要件 |
|---|---|
| 端末 | スマホ中心。片手で操作できるレイアウト、大きめのタップ領域 |
| 起動 | ホーム画面から起動できる |
| オフライン | 買い物リストは電波が弱い店内でも表示・チェックできる(復帰時に同期) |
| 同期 | 買い物チェックは2人の端末間でリアルタイム同期 |
| 認証 | **Supabase Auth の Google ログイン**。**許可リスト(household_members)に登録されたメールアドレスのみ**利用可。要求スコープは email / profile のみ |
| 認可 | Supabase の RLS で「自分の世帯のデータのみ」読み書き可能にする |
| 可用性 | Supabase 無料枠は1週間アクセスがないと一時停止するため、定期的に API を呼ぶ keep-alive ジョブを置く |
| データ共有 | 世帯(household)単位で共有 |
| 運用 | 個人運用のため、マネージドサービス・サーバーレスで保守負担を最小化 |
| 安全性 | アレルギー食材の除外は LLM の指示とロジック照合の二重チェック |

## 8. データの概略

```
households ─┬─ household_members (ログインできる人の許可リスト。auth.users とメールで対応)
            ├─ members           (食べる人。栄養計算・アレルギー用)
            ├─ settings
            ├─ meal_plans ── meal_plan_days ── dishes ── dish_ingredients
            ├─ leftovers         (余り物)
            ├─ shopping_lists ── shopping_items
            └─ favorite_recipes
ingredients(マスタ:正規名、ジャンル、日持ち目安、成分表の食品番号)
```

ログインする人(`household_members`)と食べる人(`members`)を分けることで、ログインしない家族(将来の子どもなど)も献立・栄養計算の対象に追加できる。

## 9. 主要フロー

```
[期間を指定] → [各日のモードを設定: 通常/時短/なし] → [余り物を入力]
     → [献立提案] ⇄ [一部の日・品を再提案]
     → 確定 → [買い物リスト生成(なしの日を除外、余り物を差し引き)]
     → [スーパーでチェック(2人で同期)]
     → 調理後 → [評価・お気に入り保存] → 次回の提案に反映
```
